# 完整执行工作流

本文供 Codex 执行，不要求用户手工完成技术步骤。所有命令都应根据现场安装版本和路径重新发现，不照抄旧机器上的端口、实例编号或数据库路径。

## A. 只读预检

收集并报告：

- 备份目录是否存在、文件数、总大小、最新修改时间和所在磁盘可用空间。
- MuMu 管理器、专用实例、ADB 以及实例序列号/端口。
- 电脑 QQ、Ollama 和目标模型是否可用。
- 心印共鸣项目或 EXE 是否存在，应用是否正在运行。
- 用户给出的目标联系人显示名和自己的显示名是否足以区分。

先运行 `scripts/preflight.ps1`。如果工具安装在自定义目录，可额外只读查询注册表、正在运行的进程和快捷方式；不要假定历史路径仍然有效。

磁盘空间建议至少为备份总大小的三倍，且不低于 5 GB，以容纳恢复、快照和导出文件。

## B. 隔离实例和 QQ 安装

1. 创建名为 `XinYin-QQ-Isolated` 的专用 MuMu 实例，记录实例索引、设备序列号、Android 版本和管理器版本。
2. 后续每条管理器/ADB 命令都绑定该实例；先用设备型号和已安装包列表复核目标。
3. QQ 优先通过模拟器内可信应用商店或 QQ 官方来源安装。
4. 验证 Android 包名为 `com.tencent.mobileqq`，记录版本、安装包 SHA-256 和来源。
5. 不在该实例安装无关软件，不登录无关账号，不创建端口监听或开机自启脚本。

## C. 登录和官方恢复

1. 打开模拟器 QQ，在登录、扫码、验证码或设备确认界面暂停，由用户本人操作。
2. 用户确认“已登录”后，复核账号显示信息，但不要读取或记录密码、令牌和登录二维码。
3. 在电脑 QQ 的官方“聊天记录备份与恢复”功能中选择恢复到手机/模拟器，并按 QQ 提示让双方处于同一可信局域网。
4. 等待 QQ 明确显示恢复完成。不要仅凭文件数量增长判断完成。
5. 在模拟器 QQ 中确认目标联系人的会话存在，并抽查最早/最新日期是否合理；不得把正文抄入日志。

如果 QQ 不允许把已有电脑备份恢复到模拟器，先记录准确界面和版本，再判断是否存在官方版本兼容问题。不要用随机“修复器”覆盖原始备份。

## D. 制作一致性快照

1. 等待恢复完成后至少让 QQ 完成界面刷新和磁盘写入。
2. 正常退出或通过包管理器强制停止 `com.tencent.mobileqq`，确认进程不再写数据库。
3. 动态定位 NT 消息数据库，不硬编码账号、哈希目录或版本专属路径。
4. 复制数据库主文件以及存在的 `-wal`、`-shm` 文件到时间戳工作目录。
5. 对每个文件记录相对路径、大小、修改时间和 SHA-256。清单不得包含数据库密钥、QQ 号或内部 UID。
6. 所有后续操作均针对工作副本；源文件和电脑备份不修改、不移动、不删除。

WAL 必须与主数据库来自同一个静止时点。缺少应当存在的 WAL、复制期间尺寸变化或 SQLite 完整性失败时，重新制作快照，而不是在唯一副本上修复。

## E. 判断格式并离线处理

1. 读取文件头并尝试 SQLite 只读连接；如果可列出表，则按普通 SQLite 处理。
2. 若加密，先识别 QQ 版本、数据库格式和当前工具支持范围，再审阅拟用离线工具的源码、发布来源、许可证和联网行为。
3. 不从 QQ 进程内存取密钥，不注入、不 Hook、不关闭安全软件。
4. 只对快照副本离线解密，秘密不得出现在命令行和日志中。
5. 对产物运行 `PRAGMA integrity_check`，记录表数量和消息表行数；原始快照仍保留。
6. 解析会话/联系人映射，确保目标为 C2C 私聊，且自己的 UID 与对方 UID 没有颠倒。

## F. 导出目标联系人

使用 `scripts/qq_nt_export.py` 读取已解密数据库。该脚本应保持：只读 URI 连接、目标 C2C 过滤、原子写入、URL/二进制/内部标识清理和解析失败计数。

导出后验证：

- JSON 能重新解析，顶层模式符合心印共鸣导入器。
- 消息数大于零，时间戳单调，最早和最新日期合理。
- `self-name` 与 `peer-name` 映射正确。
- 文本、图片占位、语音/文件等类型统计合理。
- 输出不包含内部 UID、数据库密钥、HTTP URL、Base64/二进制块和无关联系人消息。
- 终端只报告统计，不打印消息内容。

若存在同名联系人，使用本地会话元数据、头像哈希或用户在界面中的明确选择消歧；不要把候选人的聊天正文全部导出供人工挑选。

## G. 导入和角色蒸馏

1. 启动心印共鸣并导入 JSON，记录导入器给出的格式、数量和错误统计。
2. 在抽样预览中确认“我/对方”方向无误；发现颠倒立即停止蒸馏并重新导出。
3. 默认使用本地 Ollama，先验证模型标签和 API 可达。
4. 对 30B 至 40B 模型，先用 `num_ctx=8192`、较低温度、分块输出约 700 tokens、最终汇总约 1800 tokens、`keep_alive=30m`。从全时间范围均匀抽取约 800 条，避免只学习最近阶段。
5. 若内存/显存溢出，先减少上下文和样本量，不切换到未经授权的云端模型。
6. 角色草稿应区分：明确事实、稳定相处模式、低置信推断和不应继承的敏感信息。不得把玩笑、争执中的话或单次事件无条件固化为人格事实。
7. 用户可审阅后再保存正式角色；若用户已明确授权自动完成，可创建后仍展示不含原文的摘要和置信边界。

## H. 端到端验证

1. 选择新角色并进入聊天界面。
2. 发送一条通用测试消息，不引用隐私原文。
3. 确认 Ollama 实际收到请求、本地模型返回成功、UI 显示回复且角色没有错位。
4. 若不能进入聊天，检查角色 ID/选择状态、路由、模型标签、上下文上限和应用日志，修复后重试。

## I. 最终报告

报告只包含：

- 备份、工作快照、导出 JSON 和角色文件的绝对路径。
- 工具/QQ/模拟器/模型版本。
- 文件哈希、消息总数、类型统计、时间范围和解析失败数。
- 身份方向、导入、蒸馏和聊天验证是否通过。
- 保留了哪些本地副本，以及哪些清理动作仍需用户批准。

不要在报告中出现聊天正文、QQ 号、内部 UID、数据库密钥、登录令牌或二维码。
